5  Implementation

5.1 Development environment

The repository is a two-workspace npm project. client/ holds the React application, convex/ holds the deployed functions and schema, and shared/ holds framework-free domain modules imported by both the functions and the audit engine. The legacy Express server remains in server/ for reference but is neither built nor deployed.

One practical constraint shaped the tooling: the Convex CLI fails when the project path contains non-ASCII characters, and the project directory is Iṣẹ́. Deployment therefore runs from an ASCII working copy that links to the real convex/ and shared/ directories. The limitation and the workaround are documented in the repository README so that the project can be rebuilt elsewhere without rediscovering it.

5.2 Schema and validators

Each table is declared with Convex validators, which serve simultaneously as the database schema, the argument contract for functions and the source of the generated TypeScript types. The excerpt below is the identity core of the schema: organisations, users and sessions, with the indexes that the authentication path depends on. 

const role = v.union(v.literal('CANDIDATE'), v.literal('RECRUITER'), v.literal('ADMIN'));

export default defineSchema({
  organisations: defineTable({
    name: v.string(),
    slug: v.string(),
    sector: v.optional(v.string()),
    size: v.optional(v.string()),

    updatedAt: v.number(),
  }).index('by_slug', ['slug']),

  users: defineTable({
    email: v.string(),
    passwordHash: v.string(),
    fullName: v.string(),
    role,
    phone: v.optional(v.string()),
    organisationId: v.optional(v.id('organisations')),
    emailVerifiedAt: v.optional(v.number()),
    isActive: v.boolean(),
    lastLoginAt: v.optional(v.number()),
    deletedAt: v.optional(v.number()),
    createdAt: v.number(),
    updatedAt: v.number(),
  })
    .index('by_email', ['email'])
    .index('by_organisation', ['organisationId'])
    .index('by_role', ['role']),

  sessions: defineTable({
    userId: v.id('users'),
    tokenHash: v.string(),
    expiresAt: v.number(),

    createdAt: v.number(),
    userAgent: v.optional(v.string()),

Two details are deliberate. sessions.tokenHash is the only place a session credential appears, and it is a hash. users.deletedAt exists because erasure under the NDPA anonymises an account while retaining the decision records that reference it, so deletion cannot be a hard delete of the row.

Listing 5.2 — Evidence and application tables (convex/schema.ts, excerpt)

The by_job_candidate index is what allows the apply mutation to reject a duplicate application cheaply, and by_job_stage is the index behind the three-column board: each column is one indexed range read rather than a full scan filtered in memory. The application row keeps the human decision fields on the same record as the recommendation (aiRecommendedStage beside overrideReason), which is what makes override asymmetry computable in the audit. publicRef is a short human-quotable reference for candidates; the anonymous reference shown in the blind board is not stored at all — it is an HMAC of the application id keyed with APP_SECRET, computed at read time, so it cannot drift or be looked up in reverse.

5.3 Registration, login and sessions

Authorization is centralised rather than repeated. Every function begins with requireUser(ctx, args.token), which hashes the presented token, looks up the session by hash, rejects expired or revoked sessions, loads the user, rejects inactive or erased accounts, and returns a context containing the user, role and organisation. Scope checks are separate helpers, because they need the entity being touched. 

/** Recruiter and admin views are scoped to one organisation. */
export function requireOrg(auth: AuthContext): Id<'organisations'> {
  if (!auth.orgId) fail('FORBIDDEN', 'Your account is not linked to an organisation.');
  return auth.orgId;
}

export async function assertJobAccess(
  ctx: QueryCtx | MutationCtx,
  auth: AuthContext,
  jobId: Id<'jobs'>,
) {
  const job = await ctx.db.get(jobId);
  if (!job) fail('NOT_FOUND', 'Job not found');
  if (auth.role !== 'ADMIN' && job.organisationId !== auth.orgId) fail('FORBIDDEN', 'You do not have access to that job.');
  return job;
}

export async function assertApplicationAccess(
  ctx: QueryCtx | MutationCtx,
  auth: AuthContext,
  applicationId: Id<'applications'>,
) {
  const application = await ctx.db.get(applicationId);
  if (!application) fail('NOT_FOUND', 'Application not found');
  const job = await ctx.db.get(application.jobId);
  if (!job) fail('NOT_FOUND', 'Job not found');
  if (auth.role !== 'ADMIN' && job.organisationId !== auth.orgId) fail('FORBIDDEN', 'You do not have access to that application.');
  return { application: application as Doc<'applications'>, job };
}

Listing 5.3 — Scope enforcement helpers (shared/authz.ts)

Errors are raised through a single fail(code, message) helper that throws a ConvexError with a JSON payload, which the client adapter converts back into an ApiError carrying the same status and code (Listing 5.6). This is why a cross-organisation request surfaces in the interface as a specific forbidden message rather than a generic failure.

5.4 CV upload and text extraction

Uploading is split into two steps so that the function runtime never handles a large binary. The client asks for a signed upload URL, posts the file directly to Convex file storage, and then calls the apply mutation with the resulting storage id. File size and MIME type are validated before the URL is issued. 

export const MAX_CV_BYTES = 4 * 1024 * 1024;

export const ALLOWED_MIME = [
  'application/pdf',
  'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
  'application/msword',
];

export const generateUploadUrl = mutation({
  args: { token: v.string() },
  handler: async (ctx, args) => {
    await requireUser(ctx, args.token);
    return await ctx.storage.generateUploadUrl();
  },
});

Listing 5.4 — Signed upload URL issuance (convex/files.ts)

Text extraction runs as a Node action, because both parsers are Node libraries and neither can run in the V8 function runtime. The action loads the file, dispatches on MIME type, extracts text, updates the extraction status, then calls the shared parser to produce structured CV data and triggers scoring. The status machine — pending, processing, completed, failed — is stored on the file row, so a failed extraction is visible to the candidate and retryable rather than silently leaving an unscored application.

One implementation problem is worth recording because it cost real debugging time. The PDF text extractor ships a test fixture that is loaded at import time, and its package entry point resolves to a browser build; importing the package by name inside a Node action therefore failed at bundle time. The fix was to import the library's Node entry directly (pdf-parse/lib/pdf-parse.js) and to bundle it rather than mark it external in convex.json. The lesson generalises: on a function platform, a library that works in Node is not automatically a library that works in a serverless bundler.
